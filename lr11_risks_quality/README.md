Три ризики червоної зони, які потребують регулярної уваги:

| ID | Формулювання одним рядком | score | Стратегія | Тригер |
| :-: | --- | :-: | --- | --- |
| R-06 | Вимоги інформаційної безпеки можуть не потрапити в погоджений обсяг REL-1 | 20 | `escalate` | Немає оцінки робіт і рішення спонсора щодо обсягу |

Score є початковою оцінкою ймовірності та впливу, а не статистикою інцидентів. У журналі блокерів спринтів записів немає; реалізованих ризиків у поточному реєстрі не зафіксовано.

Файл `dod.md` містить 6 умов. Кількість завершених історій, для яких проходження DoD підтверджено, наведена в розділі «Як це працює на практиці» самого `dod.md`.

Універсальне обов'язкове review другою людиною замінено повторною самоперевіркою за чеклістом і автоматизованими перевірками. Для змін автентифікації, доступу, транзакцій бронювання й аудиту передбачено окрему перевірку відповідальним фахівцем або власником процесу.

## 4. Технічний борг

| Поле | Значення |
| --- | --- |
| Записів у `techdebt.csv` | 3 |
| Разом годин на повернення | 8 |
| Стеля годин мого варіанта | 2200 |
| Борг у відсотках від стелі | 0,36% |
| Рішення pay_now / pay_later / accept | 0 / 2 / 1 |

Звідки взявся борг: D-02 виник через рішення не включати міграцію старих записів до REL-1 і створювати пілотні акаунти та ролі вручну. D-03 зберігає оцінку S-02 у 8 SP, хоча після виключення міграції оцінку для ручного налаштування ще не визначено. 

Що я свідомо не гашу і чому: D-02 приймається для обмеженого пілоту, бо старі записи не переносяться, а пілотні акаунти й ролі налаштовуються вручну.

Як я пояснив би цей борг замовнику: Для запуску пілоту потрібно вручну створити погоджені акаунти й ролі. Автоматизацію цього налаштування можна оцінити окремо, якщо ручна робота стане суттєвою.
